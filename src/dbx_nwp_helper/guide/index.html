🛡️ Databricks Network Policy Helper

Your companion guide

Build a Databricks account network policy from your workspace's real observed traffic — safely, one reviewed step at a time. This page walks through what each step does and what you're deciding. Keep it open beside your terminal.

What this tool does

It reads Databricks system tables to see how your workspace is actually used, then proposes an account network policy you review before anything is written. Two directions:

📥 Ingress (CBI)

Context-Based Ingress — who may connect in, by source IP. Built from system.access.audit.

📤 Egress (SEG)

Serverless Egress — where workloads may connect out, by destination. Built from system.access.outbound_network.

Nothing is written unless you opt in. Analysis and the proposed policy are always side-effect-free. A write happens only when you pass --create-policy and clear the review gate — and even then it defaults to log-only dry-run.

Before you start

  1. Install & authenticate

    You need uv and a Databricks workspace you can authenticate to. Auth uses the SDK's unified auth — a profile from ~/.databrickscfg, DATABRICKS_* env vars, or OAuth.

    # set up, then see the commands
uv sync
uv run dbx-nwp-helper --help

  2. Know when you need an account admin

    Analysis and proposing a policy need only workspace read on the system tables plus a SQL warehouse. Applying a policy, or identity-scoping, additionally needs account-admin credentials — separate from your workspace login — and your numeric --account-id.

    Learn more — account-admin auth
    A workspace OAuth session can't call the account API. Use --account-profile <name> pointing at an account login (databricks auth login --host <account-console-host> --account-id <id>), or set account credentials via environment variables. See the Databricks docs on unified authentication.

The commands

dbx-nwp-helper ingress — propose & apply a CBI allow-list.
dbx-nwp-helper egress — propose & apply a serverless-egress allow-list.
dbx-nwp-helper guided — an interactive Q&A wizard that walks you through either.
dbx-nwp-helper feeds — manage the local threat-intel / cloud-range cache.
dbx-nwp-helper guide — open this page.

New? Start with guided, or run ingress with no write flags to see a proposal safely:

uv run dbx-nwp-helper ingress --profile <profile> --lookback-days 30

An ingress run, step by step

This is what happens on a typical ingress run. The tool pauses between sections so you review each one; answering no aborts cleanly, writing nothing. (--yes skips the pauses for scripting.)

  1. The CLI asks you to confirm the target workspace

    Before anything else, the CLI shows exactly which workspace it's pointed at — profile, URL, and id — and asks you to confirm, so a mis-set --profile can't act on the wrong workspace. Answer no and it stops, having done nothing.

  2. Name the policy

    You're prompted for a name (blank = your profile name). It's normalised to a lowercase, id-safe form and the CLI prints the result.

  3. You confirm your runtime parameters

    After naming the policy and before the analysis runs, the CLI prints the full set of runtime parameters it's about to use — lookback window, framing, scope, mode, enrichment, and the rest — and asks you to confirm them. Check they're what you intended before the (potentially slow) analysis begins; answer no to stop. Every parameter is explained in CLI options.

  4. Analyse audit traffic & enrich

    It finds the public source IPs that successfully connected (from system.access.audit), then enriches them with open threat-intel feeds, cloud-provider and Databricks-owned IP ranges, and (optionally) RDAP ownership lookups. This is the slow part — it shows live progress.

    Learn more — what is RDAP?
    RDAP (Registration Data Access Protocol) is the successor to WHOIS: a public query to the regional internet registries (ARIN, RIPE, APNIC, …) that returns who an IP range is registered to. The tool uses it to label each observed source IP with an owner, so the proposed rules are reviewable ("Acme Corp" rather than a bare CIDR). Treat RDAP as a signal, not a source of truth — registration data can be stale, generic (a hosting provider rather than the real user), or delegated, so use it to inform your review, not to make the decision for you. It's disabled with --no-enable-rdap (but the maximum framing needs it).
    Learn more — threat-intel enrichment
    Observed IPs that fall in known-bad ranges are excluded from the allow-list and surfaced for investigation. Databricks-owned control-plane / serverless ranges you actually saw are always kept. All feeds are free, need no API key, and are cached locally.
    No candidate IPs?
    Usually the workspace uses PrivateLink/NAT (the audit log records the relay's private IP, not the user's public IP), or the public IPs only appear on account-level rows — pass --include-account-level. The CLI prints a diagnostic funnel explaining where rows dropped out. See audit system table docs.

  5. Review recently-denied inbound requests

    As part of the analysis, the tool flags source IPs that were recently blocked inbound — both IP-access-list 403s (system.access.audit) and CBI network-policy denials (system.access.inbound_network, when that table is available). Shown for context; add them as deny rules with --deny-denied-ips.

  6. Existing IP access lists — migrate them?

    If the workspace has enabled IP access lists, the tool detects them and shows their actual IP entries. Interactive runs get a pre-checked checkbox to pick exactly which entries to fold into the new CBI policy, alongside the rules learned from observed traffic — everything starts checked, so a single Enter keeps them all. Scripted runs migrate them all by default.

    Learn more — IP ACL → CBI
    The CBI policy is designed to replace the workspace's IP access lists. After the policy is created and assigned you can optionally turn the old lists off with --disable-existing-ip-acls (they're preserved and reversible; the flag is refused unless the run both creates and assigns the replacement, so it can't leave the workspace unprotected). See IP access lists docs.

  7. Select which rules to include

    By default (interactive runs) you get a checkbox to curate exactly which observed source-IP groups become allow rules — everything starts checked, so a single Enter keeps them all. Use --no-select-rules to skip the prompt.

  8. Preview the proposed policy

    The exact allow (and any deny) rules are shown before anything is written. This is the object that would be sent to the account API.

  9. Export (optional)

    --export <path> writes the proposed policy as REST-ready JSON and a best-effort Terraform file — handy for review or applying out-of-band. Works in propose-only mode.

  10. Create the policy — dry-run first

    Nothing is written until you pass --create-policy. The default --policy-mode dry_run writes a log-only block that blocks nothing — so you can review would-be denials in the network system tables first.

    Enforce with intent. --policy-mode enforce writes the blocking block and can lock users or workloads out if the allow-list is incomplete. Stay in dry_run until the logged denials are only bad actors.
    Learn more — account network policies
    See the Databricks docs on network policies for how ingress/egress blocks and enforcement modes behave.

  11. Assign to the workspace

    With --auto-assign the policy is bound to the workspace. Before creating and assigning, the tool inspects the currently-assigned policy and aborts (or warns) rather than silently clobbering PrivateLink, cross-workspace, or enforced restrictive policies.

An egress run, step by step

Prerequisite: system.access.outbound_network only logs denied egress (including dry-run would-be-denials). So stand up an egress policy in dry_run first and let it observe for a while — that's what populates the table the egress command reads.

  1. The CLI asks you to confirm the target workspace

    Just like ingress: the exact workspace (profile, URL, id) is shown and you confirm it before anything runs.

  2. Name the policy

    Prompted for a name (blank = your profile name), normalised to an id-safe form. Point a later run at this same policy with --policy-action add_to_existing to carry both ingress and egress in one policy.

  3. You confirm your runtime parameters

    Before the analysis runs, the CLI prints the runtime parameters it's about to use — lookback window, scope, mode, threat-domain blocking, and the rest — and asks you to confirm them. Answer no to stop. Every parameter is explained in CLI options.

  4. Analyse outbound traffic & classify

    It reads the observed destinations and classifies them into storage (S3 / GCS / Azure) and internet FQDNs, looking up the cloud owner of each FQDN for context.

    Learn more — blocking known-bad domains
    The allow-list itself is what stops exfiltration. As a secondary layer, --block-threat-domains matched_only|all adds known-bad domains (from the --threat-feed, default abuse.ch ThreatFox) to the policy's block-list. It only catches known bad domains, so treat it as defence-in-depth, not the primary control.

  5. Select which destinations to allow-list

    By default (interactive runs) you get two pre-checked checkboxes — one for the internet FQDNs, then one for the storage destinations (S3 / GCS / Azure) — so you curate each kind separately. Everything starts checked, so a single Enter on each keeps them all. Use --no-select-rules to skip the prompts.

  6. Preview the proposed egress

    The exact storage + internet allow rules (and any blocked domains) are shown before anything is written — the object that would be sent to the account API. Egress limits (100 internet / 100 storage) are enforced here, keeping the highest-traffic destinations.

  7. Export (optional)

    --export <path> writes the proposed policy as REST-ready JSON and a best-effort Terraform file (with a permissive ingress default). Works in propose-only mode.

  8. Create the policy — dry-run first

    Nothing is written until --create-policy. Default --policy-mode dry_run writes a restricted-but-log-only egress block, so you can confirm nothing legitimate is caught before enforcing.

    Enforce with intent. --policy-mode enforce blocks outbound traffic not on the allow-list — an incomplete list can break legitimate workloads. Stay in dry_run until the logged denials are only traffic you mean to block.

  9. Assign to the workspace

    With --auto-assign the policy is bound to the workspace. As with ingress, the tool pre-checks the currently-assigned policy and aborts rather than clobbering an enforced restrictive egress.

Combine both directions into one policy: run the first with --create-policy --policy-action create_new (a single-policy scope, not per_workspace), note the printed policy id, then run the second with --policy-action add_to_existing --existing-policy-id <id>. Each run updates only its own direction.

The safety model, in one place

  • 🛑 Opt-in writes. No write without --create-policy; a review gate confirms first.
  • 🎯 Confirm the workspace. The exact target is shown and gated before any analysis or write.
  • 🧪 Dry-run first. Default mode is log-only — it blocks nothing.
  • 🧬 Databricks-owned traffic is prioritised, never blanket-allowed. Only ranges actually seen in your traffic are kept.
  • #️⃣ IPv4 only. The CBI schema is IPv4-only; IPv6 is analysed but never placed in a policy.
  • 🧱 add_to_existing never clobbers the other direction. It replaces only its own block.
The tool generates candidate policies from observed traffic — a starting point, not guaranteed complete or correct. You are responsible for reviewing them before use. An incomplete allow-list can block legitimate users (in enforce mode) or fail to block bad ones.

CLI options — a readable reference

Every option, grouped by command — click a group to expand it. Flags without a listed default are off (false) unless noted; each takes a --no-… form to turn it off. Run dbx-nwp-helper <command> --help for the terse version.

Shared by ingress and egress
--profile <name>default: unified auth

Which Databricks config profile (from ~/.databrickscfg) to use for the workspace analysis and the SQL warehouse. If omitted, the SDK's unified auth resolves credentials from env vars / OAuth.

--warehouse-http-path <path>default: auto

The SQL warehouse to run analysis on. If omitted, a small serverless warehouse named dbx-nwp-helper is reused or created.

--warehouse-size <size>default: X-Small

Cluster size for the auto-created serverless warehouse (2X-Small, X-Small, Small, Medium, Large, X-Large, 2X-Large, 3X-Large, 4X-Large). Bump it if the analysis query is slow on a large audit log. Ignored with --warehouse-http-path.

--lookback-days <n>default: 30

How many days of system-table history to analyse (system.access.audit for ingress, outbound_network for egress).

--min-events <n>default: 1

Drop sources below this many events — a source IP (ingress) or destination (egress) must be seen at least this often to be considered.

--enable-rdap / --no-enable-rdapdefault: on

Look up ownership of observed addresses via RDAP (ingress: source-IP owners, required for maximum framing; egress: cloud owner of internet FQDNs). The slow, network-bound part of enrichment.

--refresh-feeds

Force a re-download of the cached threat-intel / cloud-range feeds before analysing.

--policy-scope <scope>default: current_workspace

current_workspace — one policy for the profile's workspace; per_workspace — one per workspace seen; all_workspaces — a single policy built from all workspaces' traffic.

--policy-mode <mode>default: dry_run

dry_run writes the log-only block (blocks nothing); enforce writes the blocking block. Stay in dry-run until logged denials are only bad actors.

--policy-name <name>default: prompted

The policy name (blank at the prompt = the profile name). The policy id for single-policy scopes; the prefix (→ <name>-ws-<id>) for per_workspace. Normalised to a lowercase, id-safe form.

--export <path>

Write the proposed policy as REST-ready JSON (and a best-effort Terraform .tf) to this path; a directory writes <policy-id>.json inside it. Single-policy scopes only; works in propose-only mode.

--create-policy

The master write switch. Nothing is written to Databricks without it — analysis and preview are always side-effect-free.

--policy-action <action>default: create_new

create_new creates a fresh policy; add_to_existing updates only this direction's block on --existing-policy-id, leaving the other direction intact.

--existing-policy-id <id>

The target policy id for --policy-action add_to_existing.

--auto-assign

After creating the policy, bind the workspace(s) to it.

--account-id <id>

Your numeric Databricks account id — required to apply a policy (and, for ingress, to resolve identities).

--account-host <url>default: derived

The account-console host. When unset, derived from the workspace's environment (AWS / Azure / GCP).

--account-profile <name>default: unified auth

A separate profile for account-level calls (a workspace login can't call the account API). See account-admin auth.

--select-rules / --no-select-rulesdefault: on

Show a pre-checked checkbox to curate exactly which rules (ingress) or destinations (egress) to include. Use --no-select-rules to keep everything. Ignored with --yes / non-interactively.

--yes, -y

Non-interactive mode: skip the step-through pauses and the review/write gates. For scripted / CI runs.

ingress only
--treat-null-status-as-success

Count audit rows with a NULL status code as successful connections (some services don't record a status).

--include-ipv6

Analyse IPv6 source addresses too. The CBI policy stays IPv4-only, so IPv6 is reported but never placed in a policy.

--include-account-level

Include account-level (workspace_id=0) audit rows — account-console / SCIM traffic. Off by default; useful when public IPs only appear on those rows.

--threat-feeds <a,b,c>default: all

Comma-separated threat-intel feeds to enrich with (see dbx-nwp-helper feeds list). Matched source IPs are excluded from the allow-list and surfaced for investigation.

--rdap-workers <n>default: 16

How many RDAP lookups to run concurrently. 1 = sequential; higher is faster but hits RIR rate limits harder.

--policy-framing <framing>default: minimal

How tightly to frame the allow-list CIDRs: minimal (exact seen), optimal, or maximum (widen to the owning block; needs RDAP).

--scoping-mode <mode>default: ip_only

Whether to scope rules beyond source IP: ip_only, ip_and_destination, ip_and_identity, or ip_identity_and_destination (identity scoping needs account admin).

--threat-deny-rules <mode>default: off

Add explicit deny rules from threat intel: off, matched_only (feeds that matched observed IPs), or all.

--deny-denied-ips

Add the recently-denied inbound source IPs (403 / CBI) as deny rules, rather than just reporting them.

--disable-existing-ip-acls

After creating and assigning the policy, turn off the workspace's IP access lists (enableIpAccessLists=false). Requires --create-policy and --auto-assign; the lists are preserved (reversible).

egress only
--source-type-filter <type>default: all

Restrict analysis to one network_source_type (blank = all source types).

--block-threat-domains <mode>default: off

Add known-bad domains to the policy's block-list: off, matched_only (only those seen in your traffic), or all.

--threat-feed <name>default: threatfox

Which threat-domain feed to use for --block-threat-domains.
